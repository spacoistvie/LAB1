# ADR-002: Микросервисная декомпозиция с Database-per-Service и событийной интеграцией через Apache Kafka

* **ID:** ADR-002
* **Статус:** принято (Accepted)
* **Дата:** 2026-09-21
* **Авторы:** Булатова Элина Эльмаровна, группа ДИФ11
* **Реестр ADR:** [docs/adr/README.md](./README.md)
* **Связано с:** [ADR-001](./ADR-001-architecture-as-code.md) (Architecture-as-Code)

---

## 1. Контекст и проблема

TradingCore — криптотрейдинговая платформа (тема 2 «Финансовая биржа»).
Ключевые требования (подробно — в README, раздел «Сценарии атрибутов качества»):

1. **ASR-1 (производительность):** стакан заявок (Order Book) должен обрабатывать
   до **100 000 op/s** (размещение/отмена заявок), latency p99 **< 5 мс** —
   критично для маркет-мейкеров.
2. **ASR-2 (отказоустойчивость):** отказ одной зоны доступности или брокера Kafka
   не приводит к потере приказов: **RPO = 0**, **RTO ≤ 30 с**, без клиентских 5xx.
3. **Целостность:** балансы ведутся как double-entry ledger; транзакции не должны
   «размазываться» между сервисами синхронным способом.

Вопрос: **как декомпозировать систему на сервисы**, чтобы Core Domain (матчинг
заявок) масштабировался независимо, отказы изолировались, а целостность данных
не опиралась на распределённые ACID-транзакции между сервисами?

## 2. Факторы решения (Decision Drivers)

- Вынести «горячий» путь (match + ведение Order Book) в изолируемый, отдельно
  масштабируемый сервис.
- Ограничить «радиус поражения» (blast radius) отказа любой подсистемы.
- Database-per-Service: исключить конкуренцию за единую схему данных.
- Независимые релизы команд при малом составе (4–6 инженеров).
- Решение обязано явно влиять на ASR-1 и ASR-2 (прослеживаемость).

## 3. Рассмотренные варианты

### Вариант A: Монолит с единственной базой данных — **отклонён**

* Преимущества: простая локальная отладка, все транзакции локальные ACID,
  минимум инфраструктуры.
* Недостатки:
  * нарушает ASR-1: матчинг (CPU-bound, append-only) и отчёты (IO-bound) делят
    один экземпляр СУБД и один процесс; 100k op/s в монолите недостижимы без
    ручного шардирования логики;
  * нарушает ASR-2: единый процесс — единая точка отказа (утечка памяти в
    отчётности кладёт всю биржу);
  * релизный цикл зависит от самой медленной команды.

### Вариант B: Монолит + worker-сервисы поверх общей базы данных — **отклонён**

* Преимущества: частичная изоляция нагрузок, постепенное выделение сервисов.
* Недостатки:
  * нарушает Database-per-Service: общая схема БД — источник высокой связности
    (coupling), миграции синхронные;
  * сервисы зависят по данным, а не по контрактам; отказ СУБД каскадный;
  * не даёт свободы выбора стека (нужны Rust + Cassandra на горячем пути).

### Вариант C: Микросервисы по bounded contexts, Database-per-Service, Kafka как Published Language — **принят**

* Каждый bounded context — один сервис и собственная СУБД.
* Core Domain (Matching Engine) — отдельный сервис: Rust + tokio, order book
  в памяти, append-only журнал матчинга в Cassandra, шардирование по торговым
  инструментам.
* Асинхронная интеграция через Kafka (at-least-once, идемпотентные потребители,
  Transactional Outbox); синхронные проверки риск-лимитов — gRPC.
* Целостность балансов локальна в Accounts & Billing; остальным контекстам
  рассылаются события (event-carried state transfer).

## 4. Решение

| Сервис | Домен | Стек | СУБД (Database-per-Service) |
|---|---|---|---|
| API Gateway | Supporting | Kong | — |
| Order Management | **Core** | Java 21 / Spring Boot | PostgreSQL |
| Matching Engine | **Core** | Rust / tokio | Apache Cassandra (audit) |
| Market Data | Supporting | Go | ClickHouse + Redis |
| Accounts & Billing | Generic | Java 21 / Spring Boot | PostgreSQL (ledger) |
| Risk & Compliance | Generic | Kotlin | PostgreSQL |
| Notifications | Generic | Node.js | PostgreSQL |

Интеграция: Kafka (topics `orders.accepted`, `trades.executed`, `book.updated`,
`balances.changed`, `notify.requested`; RF = 3) + gRPC для pre-trade validation.

## 5. Последствия

### Положительные (++)

- Независимое масштабирование «горячего» пути → достижимо ASR-1.
- Изоляция отказов (bulkhead) → достижимо ASR-2 (RPO = 0, RTO ≤ 30 с).
- Оптимальная СУБД под каждый профиль нагрузки; независимые миграции.

### Отрицательные (−−)

- Распределённая согласованность: саги, идемпотентность, Outbox — рост
  сложности разработки.
- Операционная сложность: Kubernetes, Kafka, 5 СУБД, распределённая трассировка.

### Нейтральные (○)

- Команда переходит к модели владения сервисами; часть времени уходит на SRE-практики.
- Eventual consistency в клиентском UI компенсируются WebSocket-обновлениями.
