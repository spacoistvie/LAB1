## 2. Предметная область (~1 минута)

Что умеет платформа:

1. **Торговля** — размещение лимитных и рыночных заявок трейдерами;
2. **Матчинг** — высокочастотное сопоставление заявок и ведение стакана;
3. **Market Data** — публичный поток трейдов, глубины, свечей;
4. **Счета и расчёты** — double-entry ledger балансов, комиссии;
5. **Риск-контроль** — превентивные лимиты, маржинальные правила, KYC;
6. **Нотификации** — e-mail, SMS, push, мессенджеры.

Пользователи: розничные **трейдеры** (веб/мобильный), **маркет-мейкеры** (HFT
через FIX/API), а также операторы комплаенса и интеграционные команды.

От этих функций я и пошла к критическим свойствам качества — они и мотивируют
все сценарии ASR.

## 3. Сценарии атрибутов качества — ASR (~2 минуты)

Сценарии написаны по канону **SEI** (строго 6 элементов: Source, Stimulus,
Artifact, Environment, Response, Response Measure). Их три.

**ASR-1 — Производительность стакана.**
Источник — маркет-мейкер; стимул — пиковый поток **100 000 операций в секунду**
в течение 30 минут; артефакт — Matching Engine и Order Book; окружение —
нормальный режим, пиковые рыночные часы; реакция — все заявки принимаются,
валидируются и матчатся, ни одна корректная заявка не теряется; мера —
**latency p99 ≤ 5 мс** placement→ack, p99 ≤ 20 мс до матча, 0 потерянных заявок.

**ASR-2 — Отказоустойчивость при потере зоны доступности.**
Источник — сбой инфраструктуры; стимул — внезапная потеря одной AZ под
пиковой нагрузкой; артефакт — платформа целиком (сервисы, Kafka, PostgreSQL);
реакция — оркестратор переключает трафик, репликация не теряет
подтверждённые данные; мера — **RPO = 0, RTO ≤ 30 секунд**.

**ASR-3 — Транзакционная целостность.**
Источник — трейдер, торгующий одновременно через API и веб; стимул —
конкурентные операции (вывод средств + заявки на весь баланс); артефакт —
Accounts & Billing; реакция — double-spend исключается; мера —
**0 расхождений double-entry ledger за 100 000 конкурентных операций**.

## 4. Bounded Context Canvas — Core Domain (~1.5 минуты)

Canvas составлен для ключевого контекста — **Matching Engine**, и это
осознанно **Core Domain**: сам матчинг — источник конкурентного
преимущества платформы, тот кусок, что нельзя выкупить готовым решением.

- **Зона ответственности:** матчинг заявок по алгоритму *price-time priority*,
  ведение инкрементального стакана, публикация событий `TradeExecuted`,
  `BookUpdated`, `MatchingRejected` в Kafka.
- **Ubiquitous Language:** Order, Limit/Market Order, OrderBook, PriceLevel,
  Trade, Fill, PartiallyFilled, Cancelled.
- **Inbound:** поток `orders.accepted` от Order Management (Kafka,
  at-least-once) с идемпотентностью по `orderId`.
- **Outbound:** `trades.executed` и `book.updated` в Market Data и Accounts.
- **Бизнес-инварианты:** сортировка стакана по цене-времени не нарушается;
  каждая заявка исполняется **ровно один раз**; суммарный объём Fill не
  превышает объём заявки.

Реализация — **Rust**, стакан в памяти, append-only аудит в Cassandra.

## 5. C4 System Context Diagram (~1 минута)

Уровень 1: система — **чёрный ящик**. Внутрь не заглядываем; показаны
акторы (трейдер, маркет-мейкер, комплаенс, разработчик API) и внешние
системы: банковский шлюз, e-mail/SMS-провайдеры, мессенджеры, а также
legacy-система выписок, интеграция с которой идёт через
**anti-corruption layer**. Диаграмма отвечает на вопрос «у кого система
взаимодействует и что для кого означает», не раскрывая внутренностей.

Исходник: `docs/architecture/c4-system-context.puml`, рендер в `evidence/`.

## 6. Context Map на Context Mapper DSL (~1.5 минуты)

Карта написана на **CML** — `docs/architecture/context-map.cml`, там же
PlantUML-визуализация. Ключевые границы и связи:

- **Order Management → Matching Engine:** Customer/Supplier, заказ-канал
  через Published Language — события в Kafka;
- **Matching Engine → Market Data:** Open Host Service — стакан и трейды
  публикуются как открытый API потока;
- **Accounts ↔ Order Management:** Shared Kernel — общая схема ledger;
- **Комплаенс / legacy-платёжный шлюз:** Anti-Corruption Layer;
  комплаенс в статусе U — нижележащие подстраиваются.

Каждая связь подписана паттерном прямо в CML, поэтому карта — исполняемый
артефакт, а не красивая картинка.

## 7. C4 Container Diagram (~1.5 минуты)

Уровень 2 — раскрытие внутрь:

- **Сервисы по bounded contexts:** API Gateway, Order Management,
  Matching Engine, Market Data, Accounts & Billing, Risk Engine,
  Notification Service;
- **Database-per-Service:** у каждого сервиса своя база — PostgreSQL
  для транзакционных данных, Cassandra для append-only аудита матчей,
  ClickHouse для аналитики; **общей базы нет ни у кого** — это гарантирует
  независимые релизы и отказы;
- **Apache Kafka** — событийный backbone и Published Language;
- **gRPC** — для низколатентных синхронных проверок (например, Risk →
  Order Management);
- **HTTPS/REST, WebSocket, FIX** — клиентские каналы.

## 8. ADR в MADR (~1.5 минуты)

Два решения, формат **MADR** (meta-decision record): контекст, drivers,
варианты, последствия.

**ADR-001 — Architecture-as-Code.** Тема самого процесса: исходники
диаграмм в Git, решения в MADR, обязательные рендеры в `evidence/`.

**ADR-002 — Декомпозиция на микросервисы.** Рассмотрены и **отклонены**
два варианта:

1. *Монолит с единой базой* — быстро стартует, но единый runtime не позволяет
   задать разные SLA стакану и биллингу; общая БД — точка отказа и узкое
   место по пропускной способности;
2. *Монолит + воркер поверх общей БД* — промежуточный вариант, но конкурентная
   запись в общие таблицы всё равно упирается в блокировки и тяжёлые
   ACID-транзакции.

**Принято:** микросервисы по bounded contexts, Database-per-Service,
Kafka как backbone, Transaction Outbox для консистентности событий.
Последствия: минус — операционная сложность, плюс — изоляция отказов,
масштабирование Matching Engine только по инструментам.

Каждое решение подписано трассировкой к ASR-сценариям.

## 10. Слайд-вопросы (типовые и ответы)

**Q: Что такое Open Host Service и зачем он нам?**
A: OHS — паттерн, при котором upstream-контекст публикует протокол/сервис как
открытый для всех желающих downstream-ов. У нас Market Data публикует поток
трейдов и свечей по WebSocket как открытый API — любые потребители подписываются без
индивидуальной интеграции. Это не протокол передачи, а контракт,
опубликованный как сервис.

**Q: Что такое ACL (Anti-Corruption Layer)?**
A: Прослойка на стороне downstream, адаптирующая чужой интерфейс к нашей модели.
Классика: интеграция с внешним банком и legacy-системой выписок (SOAP). Без ACL
их схема уродует наш домен; с ACL — мы переводим их данные в свои термины
(Banking Gateway Context и есть этот слой).

**Q: Что такое Published Language?**
A: Публичная схема событий Kafka (`trades.executed`, `book.updated`) —
стандартизированный язык обмена между контекстами.

**Q: Почему ClickHouse для Market Data, а не PostgreSQL?**
A: Профиль нагрузки — write-heavy поток трейдов + аналитика (агрегации свечей,
глубина). ClickHouse колоночный, сжимает time-series и делает агрегаты на
миллиардах строк на порядки быстрее OLTP-баз. Для транзакционных балансов он бы
не подошёл, но здесь ACID не нужен.

**Q: Почему Cassandra для аудита матчей?**
A: Append-only журнал, огромный write-throughput, нет реляционных связей.
Cassandra создана именно под такую запись.

**Q: Почему PostgreSQL для Order Management и Accounts?**
A: Нужны ACID-транзакции: заказы и double-entry ledger требуют строгой
консистентности (ASR-3), и объёмы здесь не колоночно-аналитические.

**Q: Почему Matching Engine — Core Domain, а не Generic?**
A: Именно матчинг генерирует конкурентное преимущество (latency, throughput).
Остальные контексты (нотификации, комплаенс) — supporting или generic, их
можно решать готовыми продуктами.

**Q: События Kafka идут at-least-once — как исключить дубли при матчинге?**
A: Идемпотентный потребитель Matching Engine по `orderId` (уникальный ключ) +
Transaction Outbox для атомарности «событие + запись».

**Q: Почему нет единой базы данных?**
A: Database-per-Service = независимые релизы и отказы; единая БД могла бы
сделать ASR-2 невыполнимым (RPO=0 между зонами).
